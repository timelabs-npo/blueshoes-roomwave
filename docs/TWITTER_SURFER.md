# Twitter Surfer: X currents and LiDAR courses

Twitter Surfer is the intended iOS game in [timelabs-npo/blueshoes-roomwave](https://github.com/timelabs-npo/blueshoes-roomwave). Personal and community X activity supplies bounded inputs for a course a player can ride. Optional, locally captured LiDAR room geometry provides another course input. Scores come from timing, movement and clean execution on that course.

The public registration draft is [X_APP_REGISTRATION.json](X_APP_REGISTRATION.json). **The owner created X app `xsurf`, and its public OAuth 2.0 Client ID is configured. No live X authentication or API read has been verified yet.** This document defines the integration and owner setup; it does not establish a working connection or a public TestFlight release. The proposed name is an independent project name, with no claim of affiliation with or endorsement by X. The owner must review current naming and branding requirements before registration and release.

## First-beta behavior

The implemented flow offers optional X sign-in and manual refresh of two sources: that account's posts and recent public community posts matching `#TwitterSurfer OR #Roomwave`. This is public recent search, not a claim to access every X Community, a complete historical feed, or the algorithmic For You timeline. There is no webhook or background event subscription in the first beta.

The integration timestamps each observation locally and requests public engagement metrics. An activity snapshot supplies bounded energy and conversation parameters. Velocity requires two real observations at least 15 seconds apart; one observation cannot establish a growth rate. A missing metric or unavailable request is unavailable data, not an invented engagement event. Duplicate posts and repeated observations must not create duplicate inputs.

The source adapters `.xInspired` and `.xLidarInspired` distinguish an activity-shaped course from a course combining activity with the player's prior custom LiDAR course. Activity sculpts terrain, ring placement and boosts. The snapshot and resulting course freeze before the run starts, so a network refresh cannot move an obstacle during a run. Likes, reposts and follower totals never add score or substitute for player skill. Ordinary offline courses remain available when sign-in, network access, API credits or hardware are unavailable.

Community queries are bounded before key generation or URL encoding. Authorization operations check their session identity before renewing or issuing a subsequent request, so a response from a disconnected session cannot start a renewal using a replacement session's credentials. These guards do not retract a request already sent to the provider.

Derived course identity includes the actual frozen activity values and the gameplay-relevant base course definition, including geometry, encounters, points and medal thresholds. A supplied activity seed alone cannot stand in for those inputs. Freshness observed when a snapshot is used does not alter that frozen course.

LiDAR is a separate, optional local input. It requires supported hardware and camera permission. The prior custom course can be combined with the same activity snapshot; it must not silently become an unrelated default course. Raw room scans, images and local capture identifiers must not be sent to X. Physical-device LiDAR behavior needs its own observed validation.

## Verify the existing X application

These steps are for the owner in the [X Developer Console](https://console.x.com/). The JSON records the reviewed settings and the current unverified integration state; it is not a provider-native import file. The owner has created `xsurf` and supplied its public OAuth 2.0 Client ID. GitHub denied repository-variable writes to this integration (HTTP 403), so the public value is checked into the app Info.plist. No consumer secret or app bearer token is included. An optional owner-managed repository variable can assert that the expected public ID equals the reviewed value in source; the workflow never rewrites that value. Changing the public ID requires a source change and review.

1. Open the existing developer application `xsurf` under the owner's approved project. Use the proposed name **Twitter Surfer** only after reviewing current branding requirements. The description should identify it as an independent, unofficial iOS surfing game using read-only authorized activity.
2. Set the website to `https://github.com/timelabs-npo/blueshoes-roomwave` and privacy policy to `https://github.com/timelabs-npo/blueshoes-roomwave/blob/main/docs/PRIVACY.md`. Check both public pages after the changes reach `main`; the privacy policy must describe the actual sign-in, token storage, fetched activity, local processing and disconnect behavior before external testing.
3. Enable OAuth 2.0 and select **Native App**, a public client, with **Read** permission. Register this callback exactly: `twitter-surfer://oauth/callback`. Keep the full callback path identical in the console and app.
4. Use Authorization Code with PKCE **S256**, random per-attempt state and verifier, and only `tweet.read users.read offline.access`. The app opens system web authentication and validates the returning state/callback. X passwords are entered with X, never collected by the game. `offline.access` permits a refresh token; access-token expiration must still be handled.
5. Commit the issued **public Client ID** to the app's `XOAuthClientID` Info.plist setting and review that source change. If the owner also sets the repository Actions variable `X_OAUTH_CLIENT_ID`, it must equal the committed value; a mismatch fails the build without changing source. Verify the value in the actual built app. A missing ID keeps connection visibly unavailable while offline play continues.
6. Confirm endpoint access and available API credits for `GET /2/users/me`, `GET /2/users/{id}/tweets`, and `GET /2/tweets/search/recent` in the console. An X social subscription does not establish developer API access. Current official docs describe prepaid usage credits; check actual console rates, entitlement and an operational spending limit before enabling requests. Do not assume the developer-owner's discounted reads apply to all beta players.
7. Test a real authorized sign-in, personal refresh, community refresh, refresh after at least 15 seconds, frozen-course start, cancellation, denied access, expired/revoked authorization, rate limiting, and disconnect on the built app. Keep provider tokens and private response data out of logs, screenshots and GitHub artifacts. Record the actual outcome before describing the X connection as working.

The authorization endpoint is `https://x.com/i/oauth2/authorize`; token exchange uses `https://api.x.com/2/oauth2/token`. Read requests use `https://api.x.com`. A native public client must not bundle a client secret or app bearer token. Store player authorization in the iOS Keychain, clear local authorization on disconnect, and provide a route to revoke the app in the player's X connected-app settings. If a backend or webhooks are added later, that is a separate design and deployment; neither is configured by this draft.
